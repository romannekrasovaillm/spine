# Задача для кодового харнесса

Реализовать WALKING SKELETON платформы B2G-закупок — сквозной срез, эмпирически доказывающий архитектуру до массовой генерации кода.

СКОП: один сценарий端到端 — заказчик создаёт извещение (regime=FZ44) → подписывает УКЭП → извещение публикуется в ЕИС → поставщик подаёт заявку с УКЭП → заявка принята. Всё по api/openapi.yaml (v1).

ОБЯЗАТЕЛЬНЫЕ ИНВАРИАНТЫ (ARCHITECTURE-SPINE.md):
- AD-1: модули извещения/заявки/пользователи — отдельные пакеты, кросс-доступ только через интерфейсы; своя схема БД на модуль.
- AD-3: отправка в ЕИС ТОЛЬКО через outbox (запись в той же транзакции БД) + eis-adapter с ретраями/экспоненциальной паузой/circuit breaker; идемпотентность по Idempotency-Key; никаких тихих fallback — неустранимая ошибка = статус publication_failed + событие-алерт.
- AD-4: аудит append-only с hash-chain (ГОСТ-хеш можно заменить SHA-256 с явным маркером замены в коде за отсутствием сертифицированного СКЗИ на стенде — маркер: FIXME-GOST с ссылкой на ADR-004).
- AD-7: signing — отдельный модуль с узким интерфейсом sign(document_hash, signer_id, purpose); реализация на skeleton — mock за тем же интерфейсом (КриптоПро подключается позже без смены контракта).
- ЕИС на skeleton — локальный эмулятор (HTTP-стаб с задержками и отказами по сценарию теста), НЕ реальный zakupki.gov.ru.

КРИТЕРИИ ПРИЁМКИ (гейт A4, проверяет fitness_check + тесты):
1. Контрактные тесты на api/openapi.yaml проходят (все 4 операции).
2. Интеграционный тест: полный сквозной сценарий FZ44 — от createNotice до bid accepted, статус публикации доведён до published через эмулятор ЕИС.
3. Тест устойчивости: при недоступном эмуляторе ЕИС подача заявок и создание извещений работают; документ копится в outbox; после «восстановления» ЕИС — публикация доезжает без дублей (дедупликация по ключу).
4. Тест аудита: цепочка hash-chain неразрывна на сквозном сценарии; UPDATE/DELETE по аудит-таблице отклоняются БД-ролью.
5. Тест идемпотентности: повторный POST с тем же Idempotency-Key возвращает тот же ресурс, без второго эффекта.
6. fitness_check по .arch-handoff/CONSTRAINTS.yaml — PASS.

СТЕК: AD-2 допускает Java 21 (Liberica)/Spring Boot 3.x или Kotlin; финальный выбор фиксировать в TASK-отчёте с обоснованием. БД — PostgreSQL 16 (в docker-compose для стенда). RabbitMQ допустимо заменить на in-process очередь для skeleton с маркером замены.

ПЛАН ОТКАТА: skeleton — новый код в чистом репозитории; откат = git revert до коммита с архитектурными артефактами (c3fa...), данные не мигрируются.

РЕЗУЛЬТАТ — headless JSON в .arch-handoff/RESULT.json: {status: pass|fail, stack_choice, tests: {passed, failed}, evidence: [пути к логам/отчётам], deviations: [список замен с маркерами], blockers: []}.

## Контракт результата

Финальный ответ обязан завершаться JSON-объектом (после него — ни символа):

```json
{"status": "complete|partial|blocked", "assumptions": [], "open_questions": [], "conflicts_with_prior_decisions": []}
```

- `status`: `complete` — выполнено полностью; `partial` — частично; `blocked` — заблокировано.
- `assumptions`: допущения, принятые при реализации.
- `open_questions`: вопросы к архитектору.
- `conflicts_with_prior_decisions`: расхождения с принятыми ранее решениями (ADR, spine).

Архитектурный контекст — `ARCHITECTURE.md`, ограничения — `CONSTRAINTS.yaml`, рубрика приёмки — `RUBRIC.yaml` (при наличии).
