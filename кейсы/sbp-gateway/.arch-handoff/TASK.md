# Задача для кодового харнесса

Реализовать walking skeleton платёжного шлюза СБП (C2B-приём) по решению в docs/solutioning.md и ADR-001..007: (1) REST API для ТСП — регистрация динамического QR/платёжной ссылки с идемпотентностью (Idempotency-Key), запрос статуса, возврат; (2) статусная машина платежа (CREATED→QR_ISSUED→PAID→CREDITED→COMPLETED, терминальные FAILED/EXPIRED/REFUNDED) с транзакционным outbox и аудит-логом; (3) мок-адаптер ОПКЦ (имитация НСПК: регистрация QR, нотификация PAID, подтверждение возврата) — ядро контрактно-независимо от транспорта, реальный протокол НСПК НЕ реализуется (внешний вход [ТРЕБУЕТ ПРОВЕРКИ]); (4) мок-адаптер АБС с идемпотентным зачислением по paymentId и списанием по refundId; (5) нотификатор вебхуков ТСП с ретраями и DLQ. Spine-инварианты из ARCHITECTURE-SPINE.md (AD-001..AD-008) обязательны: зачисление только из PAID, атомарные переходы, идемпотентность повторных доставок. Критерии приёмки — NFR из docs/nfr.md (выполнимыми на моках): лаги, идемпотентность, отсутствие двойных зачислений. Технологический стек — по выбору команды, но с обоснованием в ADR; приоритет — доказать архитектуру сквозным сценарием, а не полнотой продукта.

## Контракт результата

Финальный ответ обязан завершаться JSON-объектом (после него — ни символа):

```json
{"status": "complete|partial|blocked", "assumptions": [], "open_questions": [], "conflicts_with_prior_decisions": []}
```

- `status`: `complete` — выполнено полностью; `partial` — частично; `blocked` — заблокировано.
- `assumptions`: допущения, принятые при реализации.
- `open_questions`: вопросы к архитектору.
- `conflicts_with_prior_decisions`: расхождения с принятыми ранее решениями (ADR, spine).

Архитектурный контекст — `ARCHITECTURE.md`, ограничения — `CONSTRAINTS.yaml`, рубрика приёмки — `RUBRIC.yaml` (при наличии).
