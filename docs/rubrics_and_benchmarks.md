# Рубрики и бенчмарки

Движок рубрик архитектурного контроля (`src/rubric.rs`) и специализированные
бенчмарки solution architecture (`src/bench.rs`). Идеи — корпоративная
матрица оценки из `docs/SOURCE_BRIEF.md` §C и таксономия Macedo §D.

## Якорные рубрики

Пять готовых YAML в `assets/rubrics/` (после `arch init` —
`~/.arch-harness/assets/rubrics/`):

| Файл | Критериев | Назначение |
|---|---|---|
| `solution_architecture.yaml` | 15 | Комплексная оценка документа solution-архитектуры банка: корпоративный охват, качество решения, NFR, проверяемость, стоимость внедрения (сумма весов 100). |
| `architecture_gates.yaml` | 6 | Полнота контрольных точек A0–A5 в пакете изменения: fit → impact → trigger → human decision → evidence → drift. |
| `adr_quality.yaml` | 5 | Качество ADR: контекст и силы, альтернативы, отрицательные последствия, обратимость, статус-дисциплина (AWS AI-DLC). |
| `handoff_quality.yaml` | 5 | Качество handoff-пакета кодовому харнессу: epic-context, инварианты, критерии приёмки, headless-контракт, план отката. |
| `macedo_dimensions.yaml` | 6 | Шесть измерений таксономии Macedo (arXiv:2606.04967): спецификация, контекст, роли, исполнение, валидация, портируемость; шкала 0–2 отображена на 1–5. |

`arch rubric list` — список с числом критериев.

### Схема YAML рубрики

```yaml
name: adr_quality                 # имя (snake_case)
description: "Что измеряет рубрика"
scale_max: 5                      # максимум шкалы
origin: anchor                    # anchor | dynamic (проставляется движком)
criteria:
  - id: alternatives              # snake_case
    name: Альтернативы
    description: "Что оценивается"
    weight: 3                     # вес; сумма произвольна, нормируется при подсчёте
    anchors:                      # якоря уровней (опционально): «1» → отсутствует, «5» → образцово
      1: "Альтернатив нет"
      3: "Перечислены, но картонны"
      5: "Реальные, с честными причинами отказа"
```

Загрузка — `rubric::load`; битые файлы в каталоге пропускаются при листинге.

## LLM-судья (`rubric::evaluate`)

- Системный промпт: судья — **независимый рецензент** («ты не проектировал
  эту систему — твоя работа найти, что сломается»). Каждая оценка обязана
  опираться на **цитату-свидетельство** из текста (приводится в `rationale`);
  свидетельства нет — балл 1 с явной пометкой. Это и есть evidence-подход:
  оценка без опоры на текст запрещена.
- Оцениваемый текст усекается до 24 000 символов (`MAX_TARGET_CHARS`).
- **JSON-контракт ответа** (строго один объект, без markdown-обёрток):

```json
{"scores": [{"criterion_id": "<id>", "score": 1, "rationale": "<обоснование с цитатой>"}],
 "verdict": "<1–2 предложения: главный риск и готовность>"}
```

- Разбор терпим к обёрткам (извлечение от первой `{` до последней `}`),
  балл принимается числом или строкой с числом. При неудаче — **один retry**
  с инструкцией «только JSON»; повторная неудача — ошибка `HarnessError::Rubric`
  с фрагментом ответа.
- Постобработка: баллы клэмпятся в `1..=scale_max`; критерии, пропущенные
  судьёй, получают 1 с rationale «судья не оценил»; порядок — как в рубрике.
- **Взвешенный итог**: `weighted_total = Σ(score·weight) / Σweight`
  (0..=scale_max). Сумма весов ≤ 0 — ошибка.

### Запуск

```bash
arch rubric run adr_quality docs/adr/ADR-001-kafka.md
arch rubric run solution_architecture docs/solution.md --model deepseek-pro
```

Отчёт — markdown: таблица «критерий | вес | балл | обоснование», взвешенный
итог, вердикт, имя судьи, дата. Пишется в `reports/rubric-<name>-<timestamp>.md`.
В TUI: `/rubric list`, `/rubric run <name> <file>` (отчёт — в чат и на
вкладку «Рубрика»).

## Динамические рубрики

Под предмет оценки, которого нет в якорных, рубрика генерируется моделью
(`rubric::generate_dynamic`):

```bash
arch rubric run solution_architecture target.md \
  --dynamic-subject "ADR выбора СУБД для контура отчётности"
```

- Модель выдаёт YAML той же схемы: 5–8 критериев с весами и якорями 1/3/5.
- При заданной якорной основе (аргумент `rubric`) промпт требует сохранить
  `scale_max` и включить первые три критерия якорной рубрики — динамическая
  остаётся сопоставимой с якорной.
- Разбор терпим к ```yaml-обёртке; при неудаче — один retry «только YAML»;
  `origin` принудительно выставляется в `dynamic`.
- Дальше работает тот же `evaluate` — судья не отличает динамическую
  рубрику от якорной.

## Бенчмарки

Сценарий (`src/bench.rs::Benchmark`) — YAML:

```yaml
name: payment_integration
description: "Что измеряет сценарий"
system_prompt: "Роль испытуемой модели (как правило — промпт architect)"
task: |
  Контекст и задание...
rubric: solution_architecture     # файл в assets/rubrics или абсолютный путь
pass_threshold: 3.5               # проходной взвешенный порог
tags: [integration, adr, nfr]
```

Прогон (`bench::run`): модель отвечает на `system_prompt + task` → ответ
оценивается рубрикой **тем же провайдером** (судья = испытуемая модель) →
`passed = weighted_total >= pass_threshold`. Отчёты в `reports/`:
`bench-<name>-<model>-<timestamp>.md` (задача, ответ, таблица рубрики,
PASS/FAIL) и `.json` (сериализованный `BenchReport`).

```bash
arch bench list
arch bench run payment_integration --model deepseek
```

### Поставляемые сценарии (`assets/benchmarks/`)

Все три — про банк «Северный», порог `3.5`, рубрика `solution_architecture`.

- **`payment_integration`** `[integration, adr, nfr, c4, payments]` —
  приём онлайн-платежей на маркетплейсе через внешний PSP: C4-диаграмма
  контейнеров (mermaid) с границей PCI/КИИ, два ADR (оркестрация платежа:
  новый сервис vs модуль ядра; токенизация картовых операций), NFR с
  измеримыми целями (p99 ≤ 1.5 с при 400 rps, RTO/RPO с обоснованием RPO=0,
  идемпотентность списаний и возвратов).
- **`legacy_decomposition`** `[brownfield, decomposition, reverse-discovery,
  delta-spec, legacy]` — декомпозиция монолита ядра 22 лет (PL/SQL + Java):
  честное reverse discovery (каждое утверждение с confidence high/medium/low,
  пробелы — явно в gaps, ничего не додумывать), выделение первого контура
  отсечения, дельта-спецификация brownfield-изменения.
- **`event_driven_design`** `[event-driven, integration, consistency,
  idempotency, kafka]` — событийная интеграция доменов «Кредиты» и
  «Клиентские коммуникации»: контракты событий, модель согласованности,
  идемпотентность консьюмеров, поведение при деградации; событийные
  решения фиксируются как ADR.

### Свои бенчмарки

1. Скопируйте схему выше в `assets/benchmarks/my_bench.yaml` (или
   `~/.arch-harness/assets/benchmarks/` после `arch init`).
2. Пишите постановку как реальную задачу архитектора: контекст (ландшафт,
   регуляторика, SLA, команда) + нумерованное задание с явным форматом ответа.
3. Ссылайтесь на якорную рубрику по имени файла (без `.yaml`) или на свой
   YAML абсолютным путём. Порог подбирайте калибровкой: прогоните
   эталонную модель, посмотрите разброс, поставьте порог ниже медианы.
4. Проверка: `arch bench run my_bench --model deepseek`.
